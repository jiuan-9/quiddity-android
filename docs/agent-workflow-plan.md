## 〇、先回答一个关键顾虑：固定化工作流会不会让聊天变麻烦？

不会。编排器管的是「工具调用怎么调度」，不是「对话怎么进行」：

- 一条没有工具调用的聊天消息：从发起到回复，走的仍是现在的普通对话流，
  编排器全程零介入、零延迟、零变化（角色扮演、寒暄、情感交流完全不受影响）；
- 单次工具调用（如「现在几点」）：直接执行，与现状完全一致；
- 只有 AI 需要连续调用多次工具（如「把 notes 里的 txt 合并成 md」）时，
  编排器才接管「执行顺序」，且对用户只呈现轻量的步骤提示。

## 一、现状问题（为什么现在像「想到什么做什么」）

1. **无任务规划**：模型收到指令后直接进入工具循环，边做边想，
   复杂任务（多步骤、依赖链）容易中途改主意、重复查询、漏步骤。
2. **无工具纪律**：工具调用完全由模型自由发挥——可能先查 A 再查 B 再回头查 A，
   缺乏「先规划 → 再执行 → 再汇报」的隐性契约。
3. **无失败复盘**：工具失败后模型凭感觉重试或绕道，没有结构化的「失败 → 原因 → 备选」链路。
4. **无进度可观测**：用户只看到工具痕迹一条条闪过，不知道整体进度（第几步 / 共几步）。
5. **上下文浪费**：每轮工具循环都要重发全部历史 + 系统提示词，多轮后 token 消耗大、速度变慢。

## 二、方案 A：提示词工作流契约（轻量，聊天友好，推荐先做）

**思路**：不新增机制，只在提示词里固化「任务工作流」，用权重架构保证遵守。
纯聊天时这几行契约安静地躺在提示词里，不产生任何机制性负担。

### A1. 任务四阶段契约（写入 Agent system 提示词区 B/C）

收到指令后按以下工作流执行：
1. 计划：先在心里拆解任务，列出需要的工具与顺序（1~3 步内完成，禁止过度规划）；
2. 执行：按计划连续调用工具，一次回复内尽量做完（已有该规则，强化）；
3. 校验：对每个工具结果做真实性检查（数据是否合理、是否报错）；
4. 汇报：按用户可读的方式总结：做了什么、拿到什么、卡在哪、下一步建议。

### A2. 失败分级处置（替换现在的「凭感觉重试」）

工具失败时按以下顺序处理：
1. 重试一次（网络/瞬时类）；
2. 换等价工具（如 read_file 失败 → file_info 确认存在性）；
3. 明确告知用户失败原因与建议，禁止假装成功、禁止无限重试。

### A3. 收益与成本

- 零架构改动，只改提示词，风险最低；与第 16 项（提示词权重架构）天然衔接；
- 成本：约 1 个工作日（提示词 + 回归测试 + 真机验证）。

## 三、方案 B'：分级自适应编排器（v2 修订版，推荐后续做）

**思路**：客户端接管「多工具任务的调度」，模型只负责「决策与内容」。
核心修正：**按工具调用复杂度分级启用，聊天/单工具场景零介入**。

### B1. 分级规则

| 场景 | 编排介入 | 用户可见变化 |
| --- | --- | --- |
| 聊天消息（无工具调用） | 无 | 无（与现状完全一致） |
| 单次工具调用 | 无 | 无（直接执行） |
| 2~3 次工具调用 | 仅隐形优化 | 无感知：同参数重复调用自动去重、失败自动重试一次、结果截断整理 |
| 4 次以上复杂任务 | 完整编排 | 「第 2/4 步：正在读取通知」级进度提示 + 统一汇报完成/失败项 |

### B2. 编排器职责（仅多工具任务生效）

1. **去重与合并**：同一工具同一参数在 2 轮内重复调用 → 自动去重（缓存结果）；
   相邻可合并操作（连续 scroll）→ 合并为一次。
2. **失败路由**：失败后自动重试一次，仍失败则记录并继续后续步骤，最终统一列出「完成项 + 失败项」。
3. **进度事件**：向 UI 派发步骤级进度事件，聊天页工具痕迹升级为步骤进度条（仅复杂任务显示）。
4. **序列预检**（可选，可关闭）：执行前静态检查参数/黑名单/权限前置，避免边做边发现。
5. **探索豁免**：模型显式要求自主探索（如「先看看再说」）时跳过预检，保留灵活场景。

### B3. 收益

- 聊天体验不变，任务可靠性提升：同样的指令 → 同样的执行序列（可测试、可回放）；
- token 省 30%+（去重 + 合并 + 少一轮无效重试），复杂任务速度明显提升；
- 复杂任务有进度可感知，从「草台班子」观感升级为「专业工具」观感。

**成本**：约 4~5 个工作日（编排器 + 事件协议 + UI 进度条 + 测试矩阵）。

## 四、方案 C：会话级任务状态机（重，暂不建议）

**思路**：把 Agent 会话升级为持久化任务状态机（task id、步骤表、断点续跑）。
适用跨轮次长任务（多文件批量处理、持续监控类任务）。
**不建议现在做的原因**：复杂度高；待方案 B' 稳定后再评估。

## 五、建议

**先 A（立即做）→ 再 B'（下个版本）→ C 观察。**

- A 是纯提示词层，聊天零负担、任务立刻有条理，1 天可上；
- B' 是分级架构：聊天无感、单工具无感、复杂任务可靠，真正实现「成熟、流畅、可控」；
- 若只选一个：选 B'（对复杂任务的决定性提升 + 聊天零干扰）。

## 六、验证方式

- 单元测试：编排器纯逻辑（分级判定/去重/合并/失败路由）JVM 可测；
- 真机：同一指令（如「把 /sdcard/notes 下的 txt 汇总成一个 md 并告诉我」）
  对比实施前后：工具调用序列、token 消耗、失败处理、聊天消息是否零变化。
