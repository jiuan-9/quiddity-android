# 会话压缩流程说明（进阶级模型 · 第 39 轮及之后）

本文档说明 Quiddity Android 应用在**进阶级（ADVANCED）**模型下，从第 39 轮开始的会话压缩完整流程。

## 一、核心概念

### 1.1 「轮」（round）的定义

**以 USER 消息为锚点**。一轮对话是指：

```
[USER 消息] → [随后的所有 AI 消息 + 追加的 USER 消息] → 下一条 USER 消息之前
```

**重要：单轮的消息数不固定为 2。** 在以下场景中，单轮会包含多条消息：

| 场景 | 单轮消息数 | 说明 |
|---|---|---|
| 普通发送 | 2 条（1 USER + 1 AI） | 用户发一条，AI 回复一条 |
| **继续说** | ≥ 2 条（1 USER + N AI） | AI 回复后用户点"继续说"会再生成 N 条 AI 消息，但不会增加 USER 消息 |
| **延迟发送** | ≥ 2 条（N USER + 1 AI） | 用户在发送延迟期间继续输入并发送，会产生多条 USER 消息，直到延迟结束才发起 API 请求，AI 只回复最后那条 |
| 撤回/重发 | 不定 | 撤回不增加消息；重发生成新 AI 消息 |

**因此，"轮"以 USER 消息计数，不以总消息数计数。** 压缩/上下文裁剪的"40 轮"是指 40 条 USER 消息及夹在它们之间的所有消息。

### 1.2 压缩的是「对话记录」，不是用户行为或模型

**压缩对象**：`messages` 列表（即"对话记录"本身），按时间正序，包含：
- USER 消息的内容
- AI 消息的内容
- 任何 SYSTEM 消息

**不压缩的内容**：
- 用户行为（点击、滑动、设置变更）
- 使用的模型 ID（已由 `conv.apiCatalogId` 单独记录，不参与压缩）
- API URL、API Key（属于配置层，不属于对话记录）
- 会话级元数据（人设、用户人设、场景、记忆、壁纸、压缩摘要本身）

**压缩产物**：一段紧凑的纯文本摘要，由 AI 提取对话记录中的关键信息而成。**摘要**只作为"对话记录的浓缩版"被替换到 API 请求中，不参与"用户行为"或"模型选择"的决策。

## 三、压缩流程总览

```
用户发送消息 → ChatViewModel 收集新消息
  ↓
checkMemoryBankCompression() 判断触发条件
  ↓
满足 userRounds - lastCompressedAtRound >= memoryBankRounds
  ↓
ChatRepository.compressConversationMemory() 调用 AI 压缩对话记录
  ↓
更新 conv.compressedMemory 与 conv.lastCompressedAtRound
  ↓
下次发送：API 请求用 compressedMemory 替代早期对话记录
```

## 四、辅助函数（按"轮"裁剪消息）

为正确处理"单轮消息数不固定"的情况，[ChatRepository.kt](file:///d:/Quiddity-android/app/src/main/kotlin/com/quiddity/app/data/repo/ChatRepository.kt) 引入两个按"轮"裁剪消息的辅助函数：

### 4.1 `takeLastRounds(messages, rounds, buffer)`

**用途**：上下文裁剪，保留"最后 N 轮"的对话记录。

**算法**：
1. 遍历 `messages`，收集所有 USER 消息的下标 → `userIndices`
2. 若 `rounds >= userIndices.size`（轮数够多），返回全部
3. 否则取 `userIndices[userIndices.size - rounds]` 作为起始 USER 位置
4. 向前多取 `buffer` 条（默认 4 条）作为上一轮 AI 回复的尾巴
5. 从该下标切到末尾返回

**为什么需要 `buffer = 4`**：避免切到"AI 正在回复中"的位置，保留 4 条尾巴以维持上一轮结尾的连贯性。

**示例**（`contextLimit = 40`，80 条消息 = 40 轮普通对话）：
- `userIndices = [0, 2, 4, ..., 78]`，长度 40
- `rounds >= userIndices.size` → 返回全部 80 条

**示例**（"继续说"后，`contextLimit = 1`）：
- 消息序列：`[U1, A1, A2, A3, U2, A4]`（U1 触发的轮含 4 条，U2 触发的轮含 2 条）
- `userIndices = [0, 4]`
- `rounds = 1`，`userIndices[2 - 1] = userIndices[1] = 4`
- 返回 `messages[4..5]` → `[U2, A4]`，正确

**示例**（"延迟发送"后，`contextLimit = 2`）：
- 消息序列：`[U1, A1, U2, U3, A2]`（U2 触发的轮含 3 条：U2 + U3 + A2）
- `userIndices = [0, 2, 3]`
- `rounds = 2`，`userIndices[3 - 2] = userIndices[1] = 2`
- 返回 `messages[2..4]` → `[U2, U3, A2]`，正确（整个第二轮被完整保留）

### 4.2 `takeFromRound(messages, startRound)`

**用途**：压缩输入裁剪，取"从第 startRound 轮起"的对话记录。

**算法**：
1. 遍历 `messages`，收集所有 USER 消息的下标 → `userIndices`
2. 若 `startRound >= userIndices.size`，返回空列表（无新对话可压缩）
3. 否则取 `userIndices[startRound]` 作为起始下标
4. 从该下标切到末尾返回

**示例**（首次压缩，`startRound = 0`）：
- 条件 `startRound <= 0` → 返回全部消息

**示例**（二次压缩，`lastCompressedAtRound = 40`，已累计 80 轮）：
- `userIndices = [0, 2, 4, ..., 158]`，长度 80
- `startRound = 40`
- `userIndices[40]` = 80（第 41 个 USER 消息的下标）
- 返回 `messages[80..159]` → 最后 40 轮对话，正确

## 五、第 39 轮到第 80 轮逐步详解

### 初始状态

```
conv.contextLimit = 40（进阶级默认值）
conv.memoryBankEnabled = true（默认开启）
conv.memoryBankRounds = 40（开启时自动同步为 contextLimit）
conv.compressedMemory = ""（空，从未压缩）
conv.lastCompressedAtRound = 0
```

### 第 39 轮（不触发压缩）

用户发送第 39 条消息后，消息流收集到 `messages` 中。

`checkMemoryBankCompression()` 执行：
```kotlin
val userRounds = messages.count { it.role == Role.USER }  // = 39
val roundsSinceLastCompress = userRounds - conv.lastCompressedAtRound  // 39 - 0 = 39
if (roundsSinceLastCompress < conv.memoryBankRounds) return  // 39 < 40 → return
```

**结论：第 39 轮不触发压缩**，进入第 40 轮等待。

### 第 40 轮（首次触发压缩对话记录）

用户发送第 40 条消息。

`checkMemoryBankCompression()` 执行：
```kotlin
val userRounds = messages.count { it.role == Role.USER }  // = 40
val roundsSinceLastCompress = userRounds - conv.lastCompressedAtRound  // 40 - 0 = 40
if (roundsSinceLastCompress < conv.memoryBankRounds) return  // 40 < 40 → 不 return
```

**满足条件，进入压缩流程：**

#### 步骤 1：构造压缩 Prompt

`ChatRepository.compressConversationMemory(conv, messages)`：

```kotlin
val compressionPrompt = buildString {
    append("请对以下对话内容进行关键信息提取和压缩。\n")
    append("压缩规则：\n")
    append("1. 数字、ID、日期、金额、专有名词，必须一字不差保留。\n")
    append("2. 除此之外的修饰词、客套话、重复解释，全部删掉。\n")
    append("3. 必须解决指代不明：把「它」、「那个」、「这个」换成具体名词。\n")
    append("4. 严禁添加原文没有的信息，严禁猜测意图。\n")
    append("5. 输出一段紧凑的摘要文本，不要分段，不要使用列表格式。\n\n")

    // 首次压缩：conv.lastCompressedAtRound = 0 → 走 else 分支取全部对话记录
    append("【本次需要压缩的对话】\n")
    val newMessages = if (conv.lastCompressedAtRound > 0) {
        takeFromRound(messages, conv.lastCompressedAtRound)
    } else {
        messages  // 全部 80 条对话记录（40 轮 USER+AI 混合，含继续说/延迟发送产生的额外消息）
    }
    newMessages.forEach { msg ->
        val label = when (msg.role) {
            Role.USER -> "用户"
            Role.ASSISTANT -> "AI"
            Role.SYSTEM -> "系统"
        }
        append("[$label] ${msg.content}\n")
    }
}
```

**首次压缩发送的是第 1 轮至第 40 轮的全部对话记录**。注意：不是恰好 80 条，而是从第 1 条 USER 到第 40 条 USER 之间的所有消息（含"继续说"产生的额外 AI 消息、"延迟发送"产生的额外 USER 消息）。

#### 步骤 2：调用 AI 压缩对话记录

通过 `api.compilePersona(apiUrl, apiKey, model, userContent)` 调用云端 AI。

**输入**：压缩规则 + 全部对话记录
**输出**：压缩后的摘要文本（紧凑的一段话）

**示例摘要**：
```
"用户在 2026-07-29 创建会话，AI 身份是用户的助手。讨论了项目 A 的需求、API 集成问题、模型选择。用户在 7-15 完成首次构建，使用 MiniMax-M3 模型，第 12 轮切换到 kimi-k2.6。用户偏好深色模式，开启压缩功能，记忆轮数 40。"
```

#### 步骤 3：写回压缩结果

```kotlin
conversationRepository.updateConversation(
    conv.copy(
        compressedMemory = compressed,        // AI 返回的对话记录压缩摘要
        lastCompressedAtRound = userRounds    // 40
    )
)
```

**更新后状态**：
```
conv.compressedMemory = "用户在 2026-07-29 创建会话..."（约 100-200 字符）
conv.lastCompressedAtRound = 40
```

### 第 41 轮到第 79 轮（不触发压缩对话记录）

每轮发送后检查：
```kotlin
val roundsSinceLastCompress = userRounds - 40  // 第 41 轮 = 1, 第 79 轮 = 39
if (roundsSinceLastCompress < 40) return  // 始终 < 40
```

**这 39 轮都不会触发压缩。** 但每次发送给 API 时，会用压缩摘要替代早期对话记录，节省大量 Token。

### 第 80 轮（再次触发压缩对话记录）

`checkMemoryBankCompression()`：
```kotlin
val userRounds = 80
val roundsSinceLastCompress = 80 - 40 = 40
if (40 < 40) return  // 不 return
```

**再次满足条件，进入压缩流程。**

#### 第二次压缩的差异

```kotlin
val newMessages = if (conv.lastCompressedAtRound > 0) {
    // lastCompressedAtRound = 40，走 if 分支
    takeFromRound(messages, conv.lastCompressedAtRound)  // 从第 41 轮起取
} else {
    messages
}
```

**第二次压缩只发送第 41 轮到第 80 轮之间的对话记录**（用 `takeFromRound` 自动按 USER 消息锚点切分，不依赖消息总数）。

#### 第二次压缩的 Prompt 构造

```kotlin
if (conv.compressedMemory.isNotBlank()) {
    append("【上一次的压缩摘要】\n")
    append(conv.compressedMemory)  // 上一次的对话记录压缩内容
    append("\n\n")
}
```

AI 收到"上一次的摘要"+"新对话记录"，生成"合并后的新摘要"，包含所有关键信息 + 新增内容。

#### 写回结果

```kotlin
conv.compressedMemory = "合并后的新摘要"（保留旧 + 新增）
conv.lastCompressedAtRound = 80
```

## 六、压缩对话记录间隔说明

| 轮次区间 | 是否触发 | 压缩的对话记录范围 | 累积压缩效果 |
|---|---|---|---|
| 1-39 | 否 | - | API 收到完整对话记录 |
| **40** | **是** | **第 1-40 轮全部对话记录** | **首次压缩对话记录** |
| 41-79 | 否 | - | API 收到 1 段压缩摘要 + 最近 40 轮 |
| **80** | **是** | **第 41-80 轮对话记录** | **二次压缩对话记录，合并旧+新** |
| 81-119 | 否 | - | API 收到 1 段压缩摘要 + 最近 40 轮 |
| **120** | **是** | **第 81-120 轮对话记录** | **三次压缩对话记录** |
| ... | ... | ... | ... |

**压缩触发间隔 = memoryBankRounds = 40 轮**（与上下文记忆轮数一致）。

## 七、压缩摘要如何使用

### ChatRepository.streamAssistantReply 中的逻辑

```kotlin
val contextLimit = if (conv.contextLimit > 0) conv.contextLimit else settings.globalContextLimit
val trimmedHistory = takeLastRounds(history, contextLimit, buffer = 4)  // 按"轮"裁剪
val apiMessages = PromptBuilder.toApiMessages(systemPrompt, trimmedHistory)
```

**`PromptBuilder` 会检查 `conv.compressedMemory`**，如果非空：
- 将压缩摘要作为一条 SYSTEM 消息插入 API 请求
- 或替换掉早期的 USER/ASSISTANT 消息
- 最终发给 API 的 token 数大幅减少

### 节省的 Token 数估算

假设平均每条消息 100 token，且对话按"普通发送"（1 轮 = 2 条）：
- **未压缩**：80 轮 = 80 条消息 = 8000 token
- **首次压缩后**：1 段压缩摘要（200 token）+ 最近 40 轮 = 8200 token（无显著节省，但为后续打基础）
- **二次压缩后**：1 段合并摘要（300 token）+ 最近 40 轮 = 8300 token
- **第 N 次压缩后**：摘要稳定在 300-500 token，加上最近 40 轮 = 8300-8500 token

进阶级模型上下文窗口通常 8K-32K，压缩后可以支撑远超 80 轮的对话。

### 与"继续说"/"延迟发送"的协同

- **继续说**：单 AI 轮产生 N 条 AI 消息，`takeLastRounds` 仍按 USER 消息锚点保留整段（U + N 条 A），不会切到 AI 中间
- **延迟发送**：单 USER 轮产生 N 条 USER 消息（直到延迟结束才发 API），`takeLastRounds` 仍按 USER 消息锚点保留整段（N 条 U + 1 条 A）

## 八、用户可调整的参数

### 关闭压缩对话记录

汉堡菜单 → 数据 → 会话压缩 → 关闭开关：
```kotlin
fun updateMemoryBankEnabled(enabled: Boolean) {
    viewModelScope.launch {
        val newConv = if (enabled) {
            conv.copy(memoryBankEnabled = true, memoryBankRounds = syncRounds)
        } else {
            conv.copy(memoryBankEnabled = false)  // 关闭后停止触发压缩
        }
        conversationRepository.updateConversation(newConv)
    }
}
```

**关闭后 `compressedMemory` 保留**，再次开启时继续使用。

### 调整压缩轮数

汉堡菜单 → 数据 → 会话压缩 → 压缩轮数：
- 范围：[5, 200]
- 默认 40（与上下文记忆轮数一致）
- 调整时不影响已压缩内容

### 重置压缩

`清空聊天记录` 会同时重置压缩状态：
```kotlin
fun clearConversationMessages() {
    viewModelScope.launch {
        conversationRepository.replaceMessages(conversationId, emptyList())
        conversationRepository.updateConversation(
            conv.copy(
                compressedMemory = "",        // 清空压缩摘要
                lastCompressedAtRound = 0     // 重置压缩位置
            )
        )
    }
}
```

## 十、总结

**进阶级模型（默认压缩轮数 40）下的压缩对话记录流程：**

1. **第 1-39 轮**：API 收到完整对话记录，无压缩
2. **第 40 轮**：触发首次压缩对话记录，将第 1-40 轮的全部对话记录发送给 AI 提取关键信息
3. **第 41-79 轮**：API 只收到压缩摘要 + 最近 40 轮对话记录
4. **第 80 轮**：触发二次压缩对话记录，合并旧摘要 + 第 41-80 轮对话记录
5. **以此类推**，每 40 轮触发一次

**关键设计原则**：
- **按"轮"而非按"条"裁剪**：以 USER 消息为锚点，正确处理"继续说"/"延迟发送"导致的单轮多消息
- **压缩的是对话记录本身**：摘要只反映"说了什么"，不反映"谁点击了什么"或"用了什么模型"
- **每 40 轮触发一次**：触发间隔 = 上下文记忆轮数 = 40，进阶级模型

**进阶级模型对比完整级/基础级：**
- **完整级（FULL）**：默认 80 轮触发，间隔大，适合长对话
- **进阶级（ADVANCED）**：默认 40 轮触发，平衡性能与质量
- **基础级（BASIC）**：默认 12 轮触发，频繁压缩，适合轻量模型
